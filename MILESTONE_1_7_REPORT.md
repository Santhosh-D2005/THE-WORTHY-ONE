# Milestone 1.7 - Gameplay experience overhaul (version 0.1.7)

Objective: make each successful extraction feel earned.

**How to read the evidence.** Three kinds of testing appear in this report and are never mixed:
- **Desktop automated** - Godot test suites on the PC (simulated input).
- **Android injected input** - the real APK on the vivo V2129, driven by `adb shell input tap` (a script, not a person).
- **Human playtest** - **none has been done on 0.1.7.** Every statement about "feel" below is a design intent, not a player verdict.

---

## 1. What changed

| Area | Change |
|---|---|
| Progress | Progress is now defined by the **number of successful taps needed** (50 at level 1). Each tap adds 100 / N %, so the bar moves in small steps (2 %, then 1.67 %, ...). The label shows whole numbers 0 %, 1 %, 2 % ... 100 % and always equals the real progress. |
| Slow / same-side taps | The first tap of an attempt awards 0. A tap slower than the level's maximum gap awards 0. A same-side tap awards 0. Decay is unchanged and recognisable. |
| Difficulty | Three independent parameters: **A** taps required, **B** maximum tap gap, **C** sword resistance (taps near the top are worth slightly less). Decay and grace keep their 1.4 curves. |
| Completion | A slow extraction: rise, hold, drift toward the camera with a slight turn, lift away; camera push-in, a brief swell of sunlight, a calm level-complete card (level, time, taps, total extractions). Stronger each level up to level 11. |
| Sword | Critically damped spring for the height; no thump / tremble layers; one tween for the whole extraction. |
| Controls | Round forest discs (wood end-grain, bark rim, moss, carved groove), **no text**, ~45 % of the old footprint, pressed animation, quiet warm ring marks the next side. The touch area is still the whole screen half. |
| Audio | `GameAudio` node with named cues (first_tap, tap, tap_slow, planted, pull, freed, level_complete, failure). **No audio assets exist, so nothing plays** - these are clean integration points only; no placeholder sounds were invented. |
| Performance fix | The disc shader ran every frame and cost 5-9 FPS on the phone; it is now rendered once into a texture (section 8). |
| Kept | Pause / resume / Quit, Back, failure / retry, timers, the render-scale baseline, all test infrastructure. |

New files: `scripts/ui/forest_disc.gd`, `shaders/control_disc.gdshader`, `scripts/ui/progress_format.gd`, `scripts/systems/game_audio.gd`, `tests/experience_tests.gd/.tscn`, `tools/sword_motion`, `tools/complete_shots`, `tools/transition_timing`, `tools/difficulty_table.gd`. Version 0.1.7 (code 5).

## 5. Sword stability investigation

Cause found: height followed the progress with a per-tap step plus a thump / tremble layer, so rapid taps produced a visible jitter. Fix: spring-damped height, the extra layers removed.

Desktop measurement (`tools/sword_motion`, phone render pixels, 3 s of alternating taps, real rising progress; old = the 0.1.6 backup run with the same tool):

| Tap gap | y_jerk old -> new | y_step_max old -> new | y reversals/s old -> new | height lag old -> new |
|---|---|---|---|---|
| 300 ms | 0.74 -> 0.12 | 0.74 -> 0.25 | 0.3 -> 0.0 | 0.93 -> 1.53 |
| 220 ms | 0.77 -> 0.12 | 0.78 -> 0.26 | 2.3 -> 0.0 | 0.89 -> 1.56 |
| 120 ms | 0.81 -> 0.11 | 0.78 -> 0.33 | 0.7 -> 0.0 | 0.97 -> 1.87 |
| 70 ms | 0.73 -> 0.11 | 0.85 -> 0.53 | 0.0 -> 0.0 | 1.14 -> 2.67 |

Sideways movement was 0 in both. The sword is steadier (jerk about 6x lower, no vertical direction flips) **at a cost**: it now lags the progress bar by 1.5-2.7 render pixels (it follows smoothly instead of snapping). That is the intended trade, but it is a real difference. This is a desktop measurement; the phone confirmed only that the build runs and the sword rises, **not** that a person sees it as stable.

## 6. Extraction reward behaviour

Sequence (level 1, about 1.9 s; longer at higher levels: hold = 0.9 + 0.6 x reward): rise (quart-out) -> hold with a slow drift toward the camera and a 0.3 rad turn -> lift away. When the blade comes free: camera push-in (-1.2 - 2.0 x reward degrees) and a short sunlight swell (no flash, no particles, no neon), then the card. Desktop tests check: one tween only, no shake on the sword, the card appears and fades, the intensity grows with the level, the next level starts cleanly. Seen on the phone: the completion card on level 1 (screenshot below). Levels 5 and 10 were completed on the phone but the screenshots missed the card (timing), so the stronger variants are desktop-verified only.

## 7. Circular control design

260 base px discs (173 px on the 720-wide phone), centred in each screen half, 100 px from the bottom. Wood end-grain with growth rings, bark rim with moss, carved groove, a soft contact shadow. Pressed: shrinks 6 % and darkens; the groove catches a faint warm light. A quiet ring marks the side to tap next. Hint text is now "ALTERNATE YOUR TAPS"; no LEFT / RIGHT text exists anywhere (test-enforced). Tapping anywhere in a half still counts (tested at the far corners). Phone screenshot: `build/shots/dev17b_playing.png`.

## 8. Android performance (vivo V2129, Adreno 610, injected taps, same-session interleaved runs)

| Build | Whole run FPS | Idle (READY) FPS | Extraction FPS |
|---|---|---|---|
| 0.1.6 | 57.2, 56.5 | 56.8, 56.9 | 58.1 and 54.8 |
| 0.1.7, live disc shader (first build) | 51.9, 50.9 | 49.1, 48.3 | about 45.7 |
| 0.1.7, `--no-discs` (diagnostic) | 58.5, 58.1 | 59.7, 59.0 | 47.1, 46.9 |
| **0.1.7 final, baked discs** | **58.4, 58.1** | **59.5, 59.1** | **47.2, 48.6** |
| 0.1.7 final, discs hidden (diagnostic) | 58.1, 57.3 | 59.5, 57.9 | 48.1, 47.8 |

The regression was the per-frame disc shader (found by hiding the discs on the same build). Rendering it once into a texture removed the cost entirely: the final build with discs equals the build without them.
**Remaining:** extraction frames run at about 47-48 FPS (1.6 was about 55-58), a cost of the new cinematic (camera push-in, light swell, drift). It lasts only about 2 s per level but is a measurable regression, not fixed. The phone warms during long sessions and FPS drifts, which is why runs were interleaved. Memory about 278 MB PSS.

Also on the phone (final build, injected taps): levels 1-10 in one run with exactly the predicted taps and no slow taps counted; the completion card; pause / resume; Back opens the pause menu; Quit exits the process; failure and retry; the stall rule; Back ignored on the failure screen (from the earlier 0.1.7 build; the final build re-ran levels 1-10 only).

## 9. Test results

Desktop automated (final code): unit 119, integration 202, failure 116, layout 256, timer 25, startup 16, pause 41, rhythm 63, experience 66 - **all pass, 0 failures**. Existing tests were not weakened; ones that encoded a deliberately changed rule (8 % per tap, rectangular panels, the 400 ms gap, disc structure) were adapted and the reason is in the test comments. One timing check in `rhythm_tests` failed once under load and passed on re-run (a flake, not a fix).
Android injected input: described in section 8.
Human playtest: **none.**

## 10. Remaining problems

1. No human playtest: tap feel, difficulty curve, the card and the discs are unjudged by a person.
2. Extraction runs at about 47-48 FPS on the phone (see section 8).
3. The sword lags the bar by 1.5-2.7 render pixels (section 5).
4. Audio cues have no assets, so the game is silent.
5. Slow, normal and rapid tapping were injected at one speed each (about 81 ms per `input tap`); a real finger varies far more, and very rapid human tapping on the phone was not tested.
6. Phone screenshots of the stronger reward at levels 5 and 10 are missing.
7. `--no-discs` remains as a debug-only switch (needs `launch_args.txt` in a debug build).
